# 軌道最適化の使い方

MOMO単段と仮定した2段機（全備約80 tの小型機と約225 tの旧基準機）のペイロード最適化に対応する。[進捗と残作業](trajectory-optimization-status.md)、[設計計画](trajectory-optimization-plan.md)、[尺度・Hessian・比較結果](optimization-numerics.md)は別文書にまとめる。

## Nativeでの実行

```sh
cargo build --locked --release --features optimization --bin openTsiolkovsky-optimize
target/release/openTsiolkovsky-optimize \
  --config examples/optimization/two_stage_80t_500km_43deg.json --output /tmp/opt-result.json
# 求解せず入力を検査
target/release/openTsiolkovsky-optimize --config examples/optimization/zero_500km_43deg.json --check
```

| 入力例（examples/optimization/） | 問題と対応範囲 |
| --- | --- |
| `hs071.json` | 4変数の既知解。最適目的値は約17.014017289 |
| `double_integrator.json` | x′=v、v′=a。静止から1,000 m先の静止へ。J=∫a²dt+3600T、解析解T=10 s・J=48,000 |
| `double_integrator_exact.json` | 同じ問題を厳密Hessian・非単位S3補正・Ruizで解く |
| `momo_single_stage.json` | MOMO Flight 3モデル。100 km頂点への追加ペイロードを最大化。射向・燃焼・スロットル固定、仰角と惰行時間を最適化 |
| `two_stage_80t_500km_43deg.json` | ブラウザの既定。全備約80 tの仮定した小型2段機（1段推進剤60 t・1,200 kN、2段12 t・110 kN）。500 km円軌道・傾斜角43°へ正味約784 kg。最大動圧付近を細かくするため1段燃焼を2フェーズに分けた8フェーズ・上段2回着火 |
| `two_stage_500km_43deg.json` | 旧基準の約225 t仮定2段機。7フェーズ。Rustの回帰試験・数値比較で使う |
| `*_coarse.json` | 求解収束と独立検証の合否が一致しないことを確認する粗メッシュ例 |
| `zero_500km_43deg.json` | 不足データを検出するテンプレート。ZERO実機の求解は未対応 |

終了コードは0=収束かつ検証合格、1=求解/検証/IO失敗、2=引数誤り、3=入力不正・未設定。反復上限や中断でも診断用の結果JSONを保存する。

## モデルと成功判定

状態は質量・ECI位置/速度の並進3DoF。J2重力、地球回転、大気、風、推進・空力を既存シミュレータと共有する。姿勢は直接指定し、回転運動やTVC応答は解かない。MOMO惰行は対気流へ瞬時整列する`aero_stable`近似、多段惰行は角度がフェーズ内で線形に変わる制御に限定する。現在のロケット最適化は一定の正の真空推力/Ispと固定スロットルに対応する。

- ペイロードを初期質量へ加え、全飛行へ影響させる。乾燥質量・搭載推進剤・予備量・投棄物・PAF・正味衛星を分ける。
- 段分離では乾燥質量と実際の残推進剤を除き、位置・速度を連続に保つ。分離インパルスは0。着火回数・イベント順序は固定する。
- 動圧、迎角、非重力比力、制御角・レートを制約する。低速迎角は円錐残差、制御多項式の角度/レートはBernstein包絡でも制限する。
- 最適化制御を初期状態から独立RK45で再積分する。イベントで停止し、後続区間をNLP状態へリセットしない。多段では推進剤累積消費も独立に積分して投棄残量を計算する。ロケットでは各区間60分割・LGR点・イベント両側、10倍厳しいRK45とも照合する。

成功には`Solve_Succeeded`と同じSI上限・検証許容値での再積分合格が必要。密な標本検査は連続時間の保証ではない。熱、回廊/落下域、相対分離、6DoF、沈降・再着火資源は未評価として結果に残す。仮定した2段機の数値はZEROの性能値ではない。

## ブラウザでの実行

```sh
rustup target add wasm32-wasip1
cd frontend
bun install
bun run dev:optimization
```

ヘッダの「軌道最適化」から開く。

1. **設定**は上から順に「出発点にする機体」→①目標と発射地点→②機体→③飛行シーケンス→④守る条件。メッシュ・初期推定・ソルバー・検証許容値・出典は折りたたんだ「詳細設定」、フォームにない構成はJSON編集。
   - ②の段表で乾燥質量・推進剤・予備・真空推力・Ispを変えると、全備質量、燃焼できる時間（`(推進剤−予備)/質量流量`を0.1 s単位で切捨て）、着火時T/W、理想Δvを表示し、`engine.burn_end_s`・`max_total_burn_s`・固定燃焼フェーズの時間・分離時刻・計算時間上限を同期する。
   - ③は各区間を「時間固定」か「範囲で最適化」で指定する。フェーズ名は段・燃焼回数・終了イベントから表示する（JSONの`name`は識別子のまま）。
   - 加速度はG、動圧はkPaで入力し、JSONにはSIで保存する。HS071・二重積分器・粗メッシュ例・旧225 t機・ZEROは「開発・検証用のケース」にまとめた。
2. **最適化を実行**で入力を固定し、別Workerで求解・検証する。「実行・結果」タブに、約0.25 s間隔で送られる途中の軌道（高度×地表距離、速度）、ペイロード、終端状態の近地点/遠地点/傾斜角、制約違反と最適性残差の履歴を表示する。途中の軌道は運動方程式を満たしていない場合がある。中断すると途中解は失われる。
3. **結果**は、判定（収束と独立検証）と「衛星○kgを高度○km・傾斜角○°へ」の要約、主要値、**ペイロードを制限している条件**（上限・下限ぎりぎりの制約。発射点の高度下限や垂直上昇直後の仰角90°など自明なものは除く）を先頭に表示する。グラフは段の色帯・分離時刻・上限線つきで、飛行経路、高度、速度、経路角、質量、残推進剤、動圧、迎角、加速度、推力、仰角、方位角、機体軸回転速度。長い惰行がある場合は「上昇部分」に表示範囲を絞れる。クリックした時刻を全グラフと地図で共有する。「条件の確認」は制約を投入・空力・加速度・姿勢・高度・推進剤・質量収支・数値整合に分け、余裕の使用率を示す。
4. **保存した実行**から復元・2件比較（グラフに灰色破線で重ねる）・入力の再編集・アーカイブ・全結果JSON保存を行う。下書きと全結果はIndexedDBへ自動保存する。

同じシーケンスで収束・検証合格した前回の結果があると「前回の結果を初期値に使う」（既定オン）を選べる。前回の再積分標本を4点に1点（各フェーズ端は保持）で`initial_guess`に入れて送る。「メッシュを細かくして再実行」は各フェーズの区間を最大2倍（1フェーズ16・合計64まで）・次数を最大8にし、元の解を初期値に使う。

入力/全結果JSONは読込ボタンかドロップで取り込める（64 MiBまで）。結果読込は記録の表示であり再検証ではない。不正ファイルは現在の設定を残して拒否する。比較では物理条件の違いを示す。メッシュ細分化は新しいcold startとして保存する。

最適化は専用の`wasm32-wasip1`とJSON ABI/WASI shimを使う。既存のwasm-bindgenシミュレータは別モジュール。Worker中断にCOOP/COEPやSharedArrayBufferは不要。

## 入出力

最適化専用の`schema_version: 1`を使い、既存シミュレータの入力・CSV・summaryは変更しない。入力には物理上限、検証許容値、尺度を別々に指定する。pounceは0.12.0固定。内部cold retryは無効化し、復元フェーズと終了理由を記録する。

多段問題の任意項目`initial_guess`（`net_payload_kg`、全フェーズの`phase_durations_s`、`samples`の`phase`・`time_s`・`state_eci`・`azimuth_deg`・`elevation_deg`）を与えると、姿勢の初期推定の順積分の代わりに、各フェーズの正規化時刻で線形補間した状態・制御・時間・ペイロードから解き始める。上下限へ丸め、フェーズ数と各フェーズ2点以上を要求する。このときIpoptの初期点の内側への押込み（`bound_push`・`bound_frac`）を1e-8にする。既定の0.01では上限90°の仰角などが0.57°動き、短い区間の姿勢レート包絡が初期点で大きく崩れる。WASIの進捗コールバックは反復記録に加え、最後に評価した点から作る`snapshot`（各ノードの時刻・フェーズ・測地高度・地表距離・慣性速度・質量、終端の近地点/遠地点/傾斜角、ペイロード）を0.25 s以上の間隔で送る。結果JSONには保存しない。

結果には入力、コードSHA、solver版、実効オプション、変数/制約名、反復履歴、全主双対、独立検証を保存する。`nlp_layout`は初期値・bounds・疎構造を含む。PR 3で追加したSI変換・数値診断のフィールドは[数値仕様](optimization-numerics.md#変換と結果json)を参照。古い結果も読める。

入力schemaの更新後は、フロントエンドの型・検査・例も同期する。

```sh
target/release/openTsiolkovsky-optimize --schema > frontend/src/lib/optimization-schema.json
cd frontend && bunx vp check --fix && bunx vp test run
```

Git情報のないソース配布ではビルド時に`OPENTSIOLKOVSKY_REVISION`を指定する。未コミットのRust変更があるビルドはrevisionに`-dirty`を付ける。

## 検証と再現

```sh
cargo test --locked --features optimization
cargo clippy --all-targets --features optimization -- -D warnings
bash scripts/optimization_wasm_build.sh
bun scripts/test_optimization_wasm.ts
python3 scripts/verify_single_stage.py
python3 scripts/verify_multi_stage.py
# 全疎成分の中心差分監査（release専用）
cargo test --release --features optimization central_jacobian_audit -- --ignored --nocapture
cd frontend && bunx vp check && bunx vp test run && bun run build
```

| S0の基準ケース | ペイロード | 再積分の最大位置差 / 速度差 |
| --- | ---: | ---: |
| MOMO | 追加16.89234 kg | 0.09141 m / 0.01463 m/s |
| 仮定した225 t 2段機 | 正味2,557.50407 kg | 2.00164 m / 0.003802 m/s |
| 仮定した80 t 2段機 | 正味783.6433 kg（全備80,333.6 kg） | 6.93 m / 0.01 m/s |

80 t機はnativeで372反復・約38 s、ブラウザでは324反復・約55 sで収束し、どちらも正味783.643 kgで検証合格する。反復経路はnative/WASIの浮動小数点差で分かれる。`scripts/test_optimization_wasm.ts`の全主双対照合は225 t機のままで、80 t機は対象外。1段の真空推力1,200 kN・Isp 300 s・ノズル出口1.2 m²で地上T/W約1.37、最大動圧60 kPaに張り付く。上段の初回燃焼の上限、長い惰行中の方位角上限130°、両段の燃焼時間上限もぎりぎりで効く。方位角範囲を60〜200°へ広げ初回燃焼上限を外すと正味約853 kgまで増えたが、惰行が2,400 s上限まで伸びて再積分位置差が10 m許容を超えたため、既定には採らない。

### ウォームスタートの効果（2026-10-19、native直列）

| 条件 | コールド | 前回解から |
| --- | --- | --- |
| 同じ問題（全標本 / 4点に1点） | 372反復・38.2 s | 238反復・25.5 s / 216反復・25.0 s |
| 2段の乾燥質量+100 kg | 517反復（並列実行） | 266反復（並列実行） |
| 目標高度600 km / 最大動圧45 kPa | 442 / 446反復（並列実行） | 340 / 330反復（bound_push既定、並列実行） |
| 粗メッシュ（区間半分・次数6）→本メッシュ | — | 441反復・15.8 s → 158反復・16.3 s（計32.1 s） |

ペイロードはどの組でも1e-3 kg以内で一致し、すべて検証合格した。最適解そのものから始めても200反復以上かかるのは、L-BFGSの曲率履歴と双対変数が初期化されるためで、内点法のウォームスタートの効果は約1.5〜2倍に留まる。`mu_init`は`mu_strategy monotone`でしか効かず、monotone + `mu_init 1e-4`はかえって反復が増えた。制約を緩めた問題を先に解いて締めていく継続法は、コールドで収束する現在の例では2回分の求解費用が増えるだけで、コールドが収束しない問題（新しい機体、厳しい制約、初期推定が遠い）で使う手段として残す。

多段基準の近地点/遠地点は499,999.9987 / 500,009.6400 m、傾斜角42.999999455°。KKT許容値1e-7で収束し、1e-8では500反復上限でも再積分は合格する。粗メッシュは単段・多段とも検証不合格。高次数化や全体の区間数増加だけでは誤差が単調に減らない。

`verify_*`は固定条件・メッシュ・3初期推定・不適合例の入力と全結果を`out/optimization/`へ保存する。native/WASI照合は全主双対とSI軌道を確認し、inactive不等式の値には一致を要求しない。多段ヤコビアン146,995成分の中心差分監査は最大規格化誤差2.33e-8。尺度・Hessianを変えた全条件は[PR 3の比較記録](optimization-numerics.md#2026-10-19の比較結果)にまとめる。
