# 軌道最適化の使い方

仮定した単段観測ロケットと2段機（全備約80 tの小型機と約225 tの旧基準機）のペイロード最適化に対応する。[進捗と残作業](trajectory-optimization-status.md)、[設計計画](trajectory-optimization-plan.md)、[尺度・Hessian・比較結果](optimization-numerics.md)は別文書にまとめる。

## Nativeでの実行

```sh
cargo build --locked --release --features optimization --bin openTsiolkovsky-optimize
target/release/openTsiolkovsky-optimize \
  --config examples/optimization/two_stage_80t_500km_43deg.json --output /tmp/opt-result.json
# 求解せず入力を検査
target/release/openTsiolkovsky-optimize --config examples/optimization/two_stage_80t_500km_43deg.json --check
```

| 入力例（examples/optimization/） | 問題と対応範囲 |
| --- | --- |
| `hs071.json` | 4変数の既知解。最適目的値は約17.014017289 |
| `double_integrator.json` | x′=v、v′=a。静止から1,000 m先の静止へ。J=∫a²dt+3600T、解析解T=10 s・J=48,000 |
| `double_integrator_exact.json` | 同じ問題を厳密Hessian・非単位S3補正・Ruizで解く |
| `single_stage_100km.json` | 仮定した単段観測ロケット（液体1段）。100 km頂点への追加ペイロードを最大化。射向・燃焼・スロットル固定、仰角と惰行時間を最適化 |
| `two_stage_80t_500km_43deg.json` | ブラウザの既定。全備約80 tの仮定した小型2段機（1段推進剤60 t・1,200 kN、2段12 t・110 kN）。500 km円軌道・傾斜角43°へ正味約784 kg。最大動圧付近を細かくするため1段燃焼を2フェーズに分けた8フェーズ・上段2回着火 |
| `two_stage_500km_43deg.json` | 旧基準の約225 t仮定2段機。7フェーズ。Rustの回帰試験・数値比較で使う |
| `*_coarse.json` | 求解収束と独立検証の合否が一致しないことを確認する粗メッシュ例 |

終了コードは0=収束かつ検証合格、1=求解/検証/IO失敗、2=引数誤り、3=入力不正・未設定。反復上限や中断でも診断用の結果JSONを保存する。

## モデルと成功判定

状態は質量・ECI位置/速度の並進3DoF。J2重力、地球回転、大気、風、推進・空力を既存シミュレータと共有する。姿勢は直接指定し、回転運動やTVC応答は解かない。単段機の惰行は対気流へ瞬時整列する`aero_stable`近似、多段惰行は角度がフェーズ内で線形に変わる制御に限定する。現在のロケット最適化は一定の正の真空推力/Ispと固定スロットルに対応する。

- ペイロードを初期質量へ加え、全飛行へ影響させる。乾燥質量・搭載推進剤・予備量・投棄物・PAF・正味衛星を分ける。
- 段分離では乾燥質量と実際の残推進剤を除き、位置・速度を連続に保つ。分離インパルスは0。着火回数・イベント順序は固定する。
- 動圧、迎角、非重力比力、制御角・レートを制約する。低速迎角は円錐残差、制御多項式の角度/レートはBernstein包絡でも制限する。
- 最適化制御を初期状態から独立RK45で再積分する。イベントで停止し、後続区間をNLP状態へリセットしない。多段では推進剤累積消費も独立に積分して投棄残量を計算する。ロケットでは各区間60分割・LGR点・イベント両側、10倍厳しいRK45とも照合する。

成功には`Solve_Succeeded`と同じSI上限・検証許容値での再積分合格が必要。密な標本検査は連続時間の保証ではない。熱、回廊/落下域、相対分離、6DoF、沈降・再着火資源は未評価として結果に残す。例題の機体はすべて仮定であり、実在の機体の性能値ではない。

## ブラウザでの実行

```sh
rustup target add wasm32-wasip1
cd frontend
bun install
bun run dev:optimization
```

ヘッダの「軌道計算 / 軌道最適化」で切り替える。2つは同じ機体モデル（シミュレータの`Config`）から派生する作業コピーを持つ。共通ヘッダは1行で、編集中のケース名、ケース情報（短いID・版・由来はボタンのツールチップとダイアログ）、Undo/Redo、ファイル操作、ヘルプと表示設定（言語・配色）を置く。切替だけでは機体を上書きしない。

軌道計算は編集後に自動更新する。最適化は共通ヘッダの「最適化を実行」（⌘/Ctrl+Enter）で明示的に開始し、実行時の入力とケース情報を固定する。切り替えてもWorkerで計算を続け、切替タブの点滅と、別画面を見ている場合の完了通知で知らせる。実行中はヘッダのボタンが「中断」（反復数付き）になる。再計算を速める前回解の利用、中断は引き続き利用できる。

デスクトップでは左に設定、右に結果を並べる（画面切替はない）。設定の幅は設定欄のタブ右端のボタンで広げられる。狭幅では両機能で共通の「設定 / 3D / グラフ」を使う。最適化結果には地図・グラフ・分割表示、共通の再生バー、PNG保存・グラフ拡大があり、時刻選択を地図とグラフで共有する。両機能の再生時刻は独立している。

**ケース保存と質量内訳**

- 「ケースを保存」は `*.otcase.json` にケースID・版・変換履歴と入力を保存する。最適化結果の「結果ケースを保存」は実行時の入力・結果・ケース情報をまとめる。下書き・保存した実行にもケース情報を保持する。共有リンクは既存の設定フラグメントを維持し、ケース情報を別の `case` フラグメントに含める。
- ヘッダのケース情報では、変換元のケース・版・実行ID・変換時の近似を見返せる。軌道計算では構造等・推進剤・投棄物・衛星/PAFの内訳も表示する。
- 最適化から渡した衛星・PAFは、軌道計算では段の全備/乾燥質量に含め、その内訳をケース情報に記録する。再び最適化へ渡すと、記録された分だけ段の質量から除き、衛星・PAFとして別に数える。構造質量や風などへの編集は残す。区間構成を変更した場合は、ケース情報で搭載区間と内訳の確認が必要になる。
- 通常のソルバー用JSONは従来と同じ入力形式で、ケース情報を含まない。既存のJSONを開いた場合、段の質量に衛星・PAFが含まれていればケース情報で「含まれている分」を指定する。ケース情報での内訳指定は段の総質量を変更しない。ソルバー用JSONだけで保存・読込した場合、内訳と履歴は復元できない。

**軌道計算との連携**（[optimization-bridge.ts](../frontend/src/lib/optimization-bridge.ts)。どちらも近似した点を注記として一覧表示する）

- **軌道計算 → 最適化**：軌道計算の「概要」タブの「この機体で最適化」、または最適化のケースメニューの「軌道計算の機体から作成」で、軌道計算で開いている機体の質量・推進・空力・射場・燃焼時刻・姿勢プログラムを読み込む。1段は単段観測ロケット、2〜4段は軌道投入の問題になり、目標軌道・ペイロード範囲・制約は、同じ軌道計算ケースから作った最適化なら編集中の設定を保ち、別の機体なら例題を基に初期化する。単段では軌道計算の結果から、目標頂点高度（頂点の75〜95%に収まらなければ頂点の90%）、最大動圧の上限（計算の最大動圧の1.2倍以上）、惰行時間の範囲、追加ペイロードの上限を機体に合わせる。多段ではペイロード範囲を全備質量に比例させ、軌道計算の最終段燃焼終了時の位置・速度から円軌道の高度と傾斜角を設定する（逆行・極軌道にも対応）。楕円軌道の機体は近地点を基にした待機円軌道に置き換え、その近似を変換履歴に明記する。下限・初期ペイロードは1 kgとし、元の位置・速度・姿勢と変換後の質量収支を初期推定に使う。動圧と加速度は機体に合わせ、燃焼で使っていた推進剤を例題の予備率で減らさず、点火遅れ0の段に余分な惰行を加えない。加速度上限はペイロード範囲の調整後に計算する。大動圧の単段機は次数8・燃焼16区間・惰行12区間、多段機の第1段燃焼は、2段機では約12秒ごとに1区間、3・4段機では16区間を基準にする。全備10 t未満の多段機は質量誤差の増幅を抑えるため求解許容値を1e-8以下にする。独立検証の物理許容値は緩めない。「概要」のカードには、全12種類のサンプルが調整後の既定設定で収束・検証合格したことを表示する（2026-10-21、native/WASI、`optimization-presets.ts`）。
  - 推力・Ispの表は総力積と推進剤消費量が同じ一定値にし、推力0の区間は惰行として燃焼を分ける（最終段の再着火前の惰行と燃焼時間は範囲で最適化、他は時間固定）。点火遅れは分離後の惰行、2段目以降の最初の投棄物はフェアリングになる。衛星質量を探す範囲は全備質量の比で例題から拡大・縮小する。
  - 姿勢プログラムの各フェーズ終了時の値を姿勢の初期推定にする。推力トリム・ランチャー・初速度は外す。CSVファイル参照の表、`cn_table`、乾燥質量のない段は変換できない。
  - ケースに記録された衛星・PAFは自動で差し引く。内訳がない既存のJSONでは、軌道計算側のケース情報で含まれる量を指定する。実機の段と計算区間の表示名は引き継ぎ、ブースタ付き機体の区間を実機の段と混同しない。
- **最適化 → 軌道計算**：結果の「軌道計算で開く」で、最適解の方位角・仰角を姿勢プログラム（ロール・取付誤差・ジャイロバイアスは外す）（解との差0.01°以内に間引いた表）、燃焼フェーズを燃焼時間（再着火は推力表の0推力区間）、分離・フェアリング投棄の時刻を段の設定にし、ペイロードとPAFを最終段、フェアリングをその段の投棄物として質量に加えた機体を開く。計算はペイロード分離時刻で終わる。風・大気・Monte Carloでの名目外の評価にそのまま使える。フェアリング投棄後の空力面積の変化は表せない。80 t例題の記録（40点に1点の標本）から作った機体では、衛星分離時の位置差は約0.3 km、速度差は約0.1 m/s。

1. **設定**は「目標・概要」「機体」「飛行」「拘束条件」「詳細」「JSON」から選ぶ。例題はヘッダのケースメニューで選ぶ。メッシュ・初期推定・ソルバー・検証許容値・出典は「詳細」、フォームにない構成はJSON編集。
   - 機体の段表で乾燥質量・推進剤・予備・真空推力・Ispを変えると、全備質量、燃焼できる時間（`(推進剤−予備)/質量流量`を0.1 s単位で切捨て）、着火時T/W、理想Δvを表示し、`engine.burn_end_s`・`max_total_burn_s`・固定燃焼フェーズの時間・分離時刻・計算時間上限を同期する。
   - ③は各区間を「時間固定」か「範囲で最適化」で指定する。フェーズ名は段・燃焼回数・終了イベントから表示する（JSONの`name`は識別子のまま）。
   - 加速度はG、動圧はkPaで入力し、JSONにはSIで保存する。ブラウザの例題は「2段ロケット（軌道投入）」と「単段観測ロケット」の2つ。HS071・二重積分器・粗メッシュ例・旧225 t機はCLI・回帰試験用で、JSON読込でのみ開ける。
2. **最適化を実行**で入力を固定し、別Workerで求解・検証する。結果欄に、約0.25 s間隔で送られる途中の軌道（高度×地表距離、速度）、ペイロード、終端状態の近地点/遠地点/傾斜角、制約違反と最適性残差の履歴を表示する。途中の軌道は運動方程式を満たしていない場合がある。中断すると途中解は失われる。
3. **結果**は、判定（収束と独立検証）と「衛星○kgを高度○km・傾斜角○°へ」の要約、主要値、**ペイロードを制限している条件**（上限・下限ぎりぎりの制約。発射点の高度下限や垂直上昇直後の仰角90°など自明なものは除く）を先頭の折りたたみから確認できる。グラフは段の色帯・分離時刻・上限線つきで、飛行経路、高度、速度、経路角、質量、残推進剤、動圧、迎角、加速度、推力、仰角、方位角、機体軸回転速度。長い惰行がある場合は「上昇部分」に表示範囲を絞れる。クリックした時刻を全グラフと地図で共有する。「条件の確認」は制約を投入・空力・加速度・姿勢・高度・推進剤・質量収支・数値整合に分け、余裕の使用率を示す。
4. 結果欄の「保存した実行」タブ（ケースメニューからも開ける）から復元・2件比較（グラフに灰色破線で重ねる）・入力の再編集・アーカイブ・全結果JSON保存を行う。下書きと全結果はIndexedDBへ自動保存する。

拘束条件は「空力荷重」「推進・加速度」「姿勢・制御」「高度・飛行領域」のカテゴリ内で縦に増やせる構成にする。フェーズごとの条件も列を追加せず項目として表示する。結果側では推力・qαの検証ID/単位を分類でき、未知の検証項目も「その他の拘束条件」に残す。今回のUI整理では推力上限・qαの数値拘束は追加していない。追加時にはRustの入力・転写・独立検証・schemaとフォームの定義を揃える。

表示の基準を明示する。軌道計算の推力重量比は真空、最適化の1段着火時T/Wは地上推力。軌道計算の最大機軸加速度と、最適化で制限する非重力比力の大きさは異なる量である。

同じシーケンスで収束・検証合格した前回の結果があると「前回の結果を初期値に使う」（既定オン）を選べる。前回の再積分標本を4点に1点（各フェーズ端は保持）で`initial_guess`に入れて送る。「メッシュを細かくして再実行」は各フェーズの区間を最大2倍（1フェーズ16・合計64まで）・次数を最大8にし、元の解を初期値に使う。

入力/全結果JSONは読込ボタンかドロップで取り込める（64 MiBまで）。結果読込は記録の表示であり再検証ではない。不正ファイルは現在の設定を残して拒否する。比較では物理条件の違いを示す。編集中のケースと結果の入力が異なる場合は、結果の要約に注記する。メッシュ細分化は新しいcold startとして保存する。

最適化は専用の`wasm32-wasip1`とJSON ABI/WASI shimを使う。既存のwasm-bindgenシミュレータは別モジュール。Worker中断にCOOP/COEPやSharedArrayBufferは不要。


### サンプル機体の収束回帰

軌道計算用の全12サンプルを実際に飛ばして変換し、`Solve_Succeeded`と独立再積分の全検査合格を要求する。[回帰テスト](../frontend/src/lib/optimization-presets.integration.test.ts)は通常のテストでは変換・入力検査を行い、以下の指定で求解まで行う。

```sh
cargo build --release --features optimization --bin openTsiolkovsky-optimize
bash scripts/wasm_build.sh
bash scripts/optimization_wasm_build.sh
cd frontend
OPTIMIZATION_PRESETS=native bunx vp test run src/lib/optimization-presets.integration.test.ts
OPTIMIZATION_PRESETS=wasm bunx vp test run src/lib/optimization-presets.integration.test.ts
```

未編集の機体と、最新の軌道計算結果から作成するケースが対象。条件を編集した任意の機体での収束は保証しない。元の軌道計算に含まれる衛星・PAFは、ケース情報で内訳を指定しない限り乾燥質量に残り、最適化で探す質量はそれに追加する量になる。

## 入出力

多段の目標傾斜角は1°以上179°未満。最初の燃焼は垂直固定を選べるが、斜め打上げも許す。後続フェーズの垂直固定は禁止する。

最適化専用の`schema_version: 1`を使い、既存シミュレータの入力・CSV・summaryは変更しない。入力には物理上限、検証許容値、尺度を別々に指定する。pounceは0.12.0固定。内部cold retryは無効化し、復元フェーズと終了理由を記録する。

多段問題の任意項目`initial_guess`（`net_payload_kg`、全フェーズの`phase_durations_s`、`samples`の`phase`・`time_s`・`state_eci`・`azimuth_deg`・`elevation_deg`）を与えると、姿勢の初期推定の順積分の代わりに、各フェーズの正規化時刻で線形補間した状態・制御・時間・ペイロードから解き始める。上下限へ丸め、フェーズ数と各フェーズ2点以上を要求する。このときIpoptの初期点の内側への押込み（`bound_push`・`bound_frac`）を1e-8にする。既定の0.01では上限90°の仰角などが0.57°動き、短い区間の姿勢レート包絡が初期点で大きく崩れる。WASIの進捗コールバックは反復記録に加え、最後に評価した点から作る`snapshot`（各ノードの時刻・フェーズ・測地高度・地表距離・慣性速度・質量、終端の近地点/遠地点/傾斜角、ペイロード）を0.25 s以上の間隔で送る。結果JSONには保存しない。

結果には入力、コードSHA、solver版、実効オプション、変数/制約名、反復履歴、全主双対、独立検証を保存する。`nlp_layout`は初期値・bounds・疎構造を含む。PR 3で追加したSI変換・数値診断のフィールドは[数値仕様](optimization-numerics.md#変換と結果json)を参照。古い結果も読める。

入力schemaの更新後は、フロントエンドの型・検査・例も同期する。

```sh
target/release/openTsiolkovsky-optimize --schema > frontend/src/lib/optimization-schema.json
cd frontend && bunx vp check --fix && bunx vp test run
```

Git情報のないソース配布ではビルド時に`OPENTSIOLKOVSKY_REVISION`を指定する。未コミットのRust変更があるビルドはrevisionに`-dirty`を付ける。

| 仮定した80 t 2段機 | 正味783.6433 kg（全備80,333.6 kg） | 6.93 m / 0.01 m/s |

80 t機はnativeで372反復・約38 s、ブラウザでは324反復・約55 sで収束し、どちらも正味783.643 kgで検証合格する。反復経路はnative/WASIの浮動小数点差で分かれる。`scripts/test_optimization_wasm.ts`の全主双対照合は225 t機のままで、80 t機は対象外。1段の真空推力1,200 kN・Isp 300 s・ノズル出口1.2 m²で地上T/W約1.37、最大動圧60 kPaに張り付く。上段の初回燃焼の上限、長い惰行中の方位角上限130°、両段の燃焼時間上限もぎりぎりで効く。方位角範囲を60〜200°へ広げ初回燃焼上限を外すと正味約853 kgまで増えたが、惰行が2,400 s上限まで伸びて再積分位置差が10 m許容を超えたため、既定には採らない。

### ウォームスタートの効果（2026-10-19、native直列）

| 条件 | コールド | 前回解から |
| --- | --- | --- |
| 同じ問題（全標本 / 4点に1点） | 372反復・38.2 s | 238反復・25.5 s / 216反復・25.0 s |
| 2段の乾燥質量+100 kg | 517反復（並列実行） | 266反復（並列実行） |
| 目標高度600 km / 最大動圧45 kPa | 442 / 446反復（並列実行） | 340 / 330反復（bound_push既定、並列実行） |
| 粗メッシュ（区間半分・次数6）→本メッシュ | — | 441反復・15.8 s → 158反復・16.3 s（計32.1 s） |

ペイロードはどの組でも1e-3 kg以内で一致し、すべて検証合格した。最適解そのものから始めても200反復以上かかるのは、L-BFGSの曲率履歴と双対変数が初期化されるためで、内点法のウォームスタートの効果は約1.5〜2倍に留まる。`mu_init`は`mu_strategy monotone`でしか効かず、monotone + `mu_init 1e-4`はかえって反復が増えた。制約を緩めた問題を先に解いて締めていく継続法は、コールドで収束する現在の例では2回分の求解費用が増えるだけで、コールドが収束しない問題（新しい機体、厳しい制約、初期推定が遠い）で使う手段として残す。

多段基準の近地点/遠地点は499,999.9987 / 500,009.6400 m、傾斜角42.999999455°。KKT許容値1e-7で収束し、1e-8では500反復上限でも再積分は合格する。粗メッシュは単段・多段とも検証不合格。高次数化や全体の区間数増加だけでは誤差が単調に減らない。

`verify_*`は固定条件・メッシュ・3初期推定・不適合例の入力と全結果を`out/optimization/`へ保存する。native/WASI照合は全主双対とSI軌道を確認し、inactive不等式の値には一致を要求しない。多段ヤコビアン146,995成分の中心差分監査は最大規格化誤差2.33e-8。尺度・Hessianを変えた全条件は[PR 3の比較記録](optimization-numerics.md#2026-10-19の比較結果)にまとめる。

225 t多段例の制約乗数の比較は、差を`max(1, |native値|)`で割って5e-4以下とする。自由な軌道位相・昇交点赤経があり、Linux x64とWASIの乗数差が3.09e-4となるため、従来の3e-4ではCIで失敗する。両環境の収束・独立検証・双対残差を確認し、目的値・主変数・飛行の許容差は維持する。CIは比較結果を`optimization-parity`アーティファクトとして保存する。
