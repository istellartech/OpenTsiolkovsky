# Rust軌道最適化の導入計画

最終更新: 2026-10-19。外部レビュー後の版を基に、ZERO向け拘束条件・基準ミッション・スケーリングの実験計画を拡充した。API名・数値手法には設計案を含む。**完了範囲・残作業・次の順序は[trajectory-optimization-status.md](trajectory-optimization-status.md)**、実行方法と検証結果は [optimization.md](optimization.md) に記録する。現在は単段と仮定した2段機のnative/WASI求解・独立再積分、基本UIと永続化まで実装した。PR 3の尺度/Hessian比較、PR 5aの熱、PR 5bのZERO機体データ・運用条件、PR 6の追加UI要件等は未完了。公開仕様、ユーザー指定、設計上の仮定、要提供データを区別する。

## 1. 概要

OpenTsiolkovskyの物理モデルを使い、多段ロケットのペイロード最大化軌道をブラウザ内で求める。

| 項目 | 方針 |
| --- | --- |
| 離散化 | フェーズ別・固定メッシュのflipped LGR擬スペクトル法（hp分割可能な構造） |
| NLPソルバー | [pounce](https://github.com/jkitchin/pounce)（Ipopt移植の純Rust内点法）。crates.ioの `pounce-nlp` 等を版固定で利用し、Rustで `TNLP` を直接実装する |
| 微分 | 転写の線形項は解析微分、ノードの物理は [num-dual](https://docs.rs/num-dual/) による局所前進AD |
| Hessian | L-BFGS（GELATOと同じ）を既定とし、局所二階ADによる厳密Hessianを小問題で比較してから多段での既定を決める |
| 実行環境 | Web Worker上の最適化専用WASM（`wasm32-wasip1`）。Python・Pyomo・AMPL `.nl` は使わない |
| 検証 | 最適化制御を復元し、補強したRK45で独立に再積分する。投入、荷重、熱、資源、落下域等の適用制約をSI単位で再評価する |
| 基準ミッション | ZERO、500 km円軌道・傾斜角43°。公開情報だけの仮モデルと、機体データをそろえた基準モデルを区別する |
| スケーリング | 物理量による無次元化を基準とし、範囲・初期軌道・ヤコビアン・KKTの各層を比較可能にする。第5.4節の実験で既定値を決める |

着手順は「ソルバー接続の実証（PR 0）」と「物理評価の分離（PR 1）」から（第8節）。一般的な最適制御ライブラリへの抽象化は、単段・多段の実例で境界が分かってから行う。

### 1.1 基準ミッション: ZERO / 500 km / 43°

ユーザー指定の基準機体は**インターステラテクノロジズ ZERO**、目標は**高度500 km・傾斜角43°**とする。離心率の指定がないため、本計画では500 km円軌道と解釈する。通常の性能最大化ケースではRAAN・軌道上の位相・到達経度は自由とし、指定ミッションでは後から独立な条件として追加する。500 kmをSSOの指定と解釈しない。

| 項目 | 基準ケースでの扱い |
| --- | --- |
| 機体構成 | 2段・液体メタン/LOX、1段9基・2段1基という公開構成を使う。段別質量、実推力/Isp、空力、運用制約は版付き機体データとして別途設定する。 |
| 発射場 | HOSPO/大樹を基準とする。ZERO用LC-1の正確な緯度・経度・高度・初期方位・許容射向は要確認。既存MOMOサンプルの座標を実機値として流用しない。打上げUTCは各ケースで固定し、自由時刻を使う場合は別のミッション変数にする。 |
| 軌道高度 | 最初は `r_target = R_orbit_ref + 500,000 m`。`R_orbit_ref` は軌道高度用の球基準半径として明示し、初期値は既存定数のWGS84赤道半径6,378,137 mを使用する。大気・地表クリアランスには従来どおりWGS84測地高度を使う。両者を混同しない。 |
| 終端イベント | 最終の第2段停止後、ペイロード分離直後の接触軌道を目標とする。最初は分離Δv=0でよいが、燃焼停止・惰行・分離を別イベントとして保持する。実際の分離Δv・時刻を導入したら分離後の状態に条件を課す。 |
| 燃焼方式 | 最初の数値実証は直接投入の簡略ケースでもよい。ZEROの基準ケースには上段再着火を表現できる構造を用意し、許容回数・惰行時間・始動条件を機体設定で固定する。最適化中のオン/オフ切替や再着火回数の自由選択は行わない。 |
| 目的の質量 | 衛星の正味質量を最大化する。PAF・分離機構・アダプタ・フェアリング・投棄物・上段残推進剤を別に計上し、機体側質量を「ペイロード」へ紛れ込ませない。 |

[ZERO公式ページ](https://www.istellartech.com/launch/zero) は2026-10-19確認時点でLEO最大1,000 kg、傾斜角42.2°〜SSOを掲示している。一方、[Payload User’s Guide v2.0 / July 2024](https://www.istellartech.com/7hbym/wp-content/themes/ist_2023/assets/pdf/usersguide_zero.pdf) p.12の性能例は800 kg・561 km・42.2°で、版と条件が異なる。どちらも「500 km / 43°の正解ペイロード」や最適化の固定上限にはしない。ガイドp.36は上段再着火を含む代表シーケンスであり、その時刻を今回の固定条件として転載しない。

公開情報で確定しないものは、段別乾燥/推進剤/残量、PAF・投棄質量、推力/Isp/混合比/スロットル範囲・遷移、空力、q・迎角・曲げ/荷重上限、飛行回廊・落下域、再着火条件等。値がそろわない段階は「ZERO構成を参考にした仮定付き数値実証」と表示し、実機性能を評価したとは扱わない。機体仕様の不足はソフトウェア実装の着手を妨げないが、実機基準ケースの完了条件には含める。

43°への到達可能性は発射場緯度だけでなく、東向き/南向きの分岐、地球回転、許容射向・回廊で確認する。指定軌道面がないケースと、RAAN/打上げ窓まで指定したケースを分ける。

## 3. 物理評価と問題定義

### 3.1 共通評価関数

```rust
// 概念API。現行の単段用実装は src/physics/flight.rs を参照。
fn evaluate<T: DualNum<Primitive = f64> + Copy>(
    model: &FlightModel,       // 読込済みの不変データ（f64）
    phase: &PhaseContext,      // 使用段、燃焼/惰行、テーブル時刻の基準
    t: T, t_phase_start: T,    // 別入力にする（第5.2節）
    x: &FlightState<T>, u: &FlightControl<T>, p: &DesignParameters<T>,
) -> Result<FlightEvaluation<T>, EvaluationError>;
// FlightEvaluation = { dx_dt, observables: 動圧, Mach, 迎角, 推力, 質量流量, ... }
```

- 既存 `Simulator` は設定姿勢から制御を作るアダプタ経由で同じ関数を呼ぶ。テレメトリと制約計算で別の式を持たない。
- 評価はシミュレータの可変状態やI/Oに依存させない。テーブル時刻は「打上げから」「段開始から」「着火から」を区別する。
- 評価失敗（非有限値、定義域外）は `Err` とし、TNLPでは `false` を返す。Ipopt系ソルバーは評価失敗時にステップを縮めて再試行する。

**nalgebraの更新。** num-dual 0.15のnalgebra連携は `nalgebra ^0.35` / `simba ^0.10` を要求する。現行は0.32で、この版のままでは双対数の `Vector3<T>` に `norm` 等が使えず、物理を配列で書き直すことになる（共通評価経路の目的に反する）。旧構成での0.35への更新確認を最新構成へ引き継がず、PR 1でnative/WASM・C++参照・保存則の回帰を実行して更新する（num-dualは既定featureの `nalgebra` を使う）。

### 3.2 状態・制御・設計変数

- 状態: `[m, r_ECI(3), v_ECI(3)]`。内部単位はSI・rad。
- 制御: NED基準の方位角・仰角（機体+X＝推力方向、空気力にも同じ姿勢）。仰角90°付近で方位角が特異になるため、垂直上昇はフェーズを分けて姿勢固定にする。方位角の±180°折返しが区間内に入らないよう、連続な角度表現を使う。特異性が問題になる場合は、ECI推力方向の単位ベクトル（3成分＋ノルム等式）へ切り替える。
- スロットル: 初期接続試験では固定。ZERO基準ケースでは荷重上限との両立を検査し、実機が許容する段・範囲・変化率だけを自由化する。真空推力と質量流量を同時に変える。固定スロットルで荷重条件を満たせない場合、荷重上限を外して成功扱いしない。
- 設計変数: 最終段まで運ばれるペイロード質量、および自由なフェーズ時間長。

これは姿勢を直接指定する並進3DoFであり、回転の実現可能性は保証しない。初期版でも姿勢の連続性と補間した方向の変化率を制約・検証する（第3.4節）。GELATO相当の姿勢運動学はクォータニオン状態・角速度制御で拡張できるが、慣性・空力モーメント・TVC応答を含む6DoF検証は別段階とする。

### 3.3 フェーズと質量収支

フェーズは段ではなく不連続点（着火、燃焼停止、惰行、段分離、フェアリング投棄）で区切る。イベント順序と段構成は固定し、時刻だけを最適化する。微分評価中に段や燃焼モードを切り替えない。

```text
m_initial          = m_payload + Σ_s (m_dry,s + m_prop,s) + Σ m_jettison
m_after_separation = m_before - m_dry,discarded - m_residual,discarded - m_other
r, v               : 分離前後で連続（分離インパルスなし）
```

- 段ごとの累積消費 ≤ 搭載推進剤。燃焼中の全質量 ≥ 搭載中の乾燥質量＋上段＋ペイロード。
- ペイロードは初期質量を通じて全フェーズに効く。最終質量から定数を引くだけの目的にしない。
- `mass_initial` だけから内訳は復元できないので、最適化用設定に乾燥質量・推進剤量を明示入力させる。既存シミュレーション入力の意味は変えない。
- 推力履歴が固定（固体モータ等）の段は燃焼時間を伸縮させない。エンジン停止・再着火の可否を設定で明示する。

### 3.4 目的・投入条件と拘束条件の台帳

未スケール目的を `f_SI = -m_payload` とし、TNLPへ渡す目的は `minimize f_SI / F_ref` とする。`F_ref` は目的専用の質量尺度で、全機質量の尺度と同じでなくてよい。平滑化目的や実行可能性回復用スラックは別項として記録する。最終の基準ケースではハード制約の違反をペイロードと交換しない。

#### 投入条件

基準の円軌道は次の4条件を独立に課す。`h = r × v`、`r_t = r_target`、`i_t = 43°` とし、ECI位置・慣性速度を使う。

```text
c_r = (r·r - r_t²) / (2 r_t) = 0       [m]
c_v = (v·v - μ/r_t) / (2 sqrt(μ/r_t)) = 0  [m/s]
c_radial = (r·v) / |r| = 0             [m/s]
c_i = h_z / |h| - cos(i_t) = 0         [-]
```

これは元の二乗形と等価な残差表現であり、巨大な `m²` の残差を直接TNLPへ渡すことを避ける。さらに第5.4節の尺度を適用する。RAANや軌道上位相を自由にするので、6成分の位置・速度を同時に指定しない。円軌道で特異な近地点引数・真近点角や、上記と重複するエネルギー・離心率条件を追加しない。赤道軌道の別ケースでは傾斜角残差のランク退化に対応した軌道面条件へ切り替える。

最初は数値的な目標等式で解き、再積分後に近地点・遠地点・傾斜角の誤差を評価する。実ミッションの許容域を最適化に使う場合は「許容域内の性能最大化」という別設定にし、緩い境界側へ寄った解を厳密な500 km円軌道と表示しない。ガイドp.13の投入精度は実飛行の目標値であり、転写残差やRK45の数値許容値には転用しない。J2等を使う場合も、この終端条件は二体近似の接触軌道であって長期の平均軌道ではない。

#### 制約の実装・適用区分

「必要に応じて」のまま埋もれないよう、全制約を台帳に登録する。以下の **C** は初期の物理的に成立する投入問題に必要、**Z** は機体データをそろえたZERO基準ケースで適用・判定が必要、**V** は3DoF最適化の外で検証するものを示す。Zの一部は追加の状態・モデルを要するため段階導入するが、未実装やデータ未設定なら結果を「未評価」とし、適用済み扱いしない。

| RANGE / Z | 許容射向、飛行回廊、落下域、必要なら飛行中IIPの許容域 | 上昇中、分離後の第1段・フェアリング等。回転地球上の地理領域・地形・風と投棄物の伝播モデル。分離点や簡易真空IIPだけを最終着地点の代用にしない。分離時に状態を分岐し、別物体として伝播する。 |
| DEPLOY / Z | 分離姿勢/角速度、分離後の上段との離隔、投入後の上段処置の資源確保 | 最終停止、惰行、衛星分離、処置フェーズ。ミッションの終端定義と整合させる。3DoFで評価できない項目は未評価。 |
| OPERATIONS / 条件指定時Z | RAAN/打上げ窓、通信可視、追跡、指定分離位置、日照/熱・電力条件 | 適用を指定したミッションのみ。地上局・軌道面・UTC等。43°・500 kmだけから必須条件を捏造しない。 |
| GNC/ENV / V | TVCの角度・レート・制御余裕、回転運動、弾性/スロッシング、振動・衝撃・音響・圧力変化 | 6DoF/荷重解析・環境適合性。剛体3DoFだけで検証済みと表示しない。 |

[首尾一貫した打上げ機設計のNASA資料](https://ntrs.nasa.gov/citations/20010066713) は動圧、軸加速度、迎角、熱、段切替・投入等を連成した制約として扱う。フェアリング後の熱と分離段の着水域は、[Benedikter et al. (2020)](https://arxiv.org/abs/2008.13239) の最適化事例でも結合して扱われる。本台帳はこれらを参考にした本プロジェクトの要件案であり、数値上限はZEROの機体・ミッションデータで決める。

#### ZERO固有の注意とモデル拡張

- ガイドp.26のフェアリング分離時の自由分子加熱1135 W/m²は熱モデルを選ぶ根拠になるが、`ρv³/2` などの代理式と同一であるとは仮定しない。吸収係数・流れ領域・姿勢の定義を合わせてから使う。分離瞬間だけでなく、その後の上昇・惰行でも熱を確認する。
- ガイドp.21の軸/横の準静的荷重は連成した包絡で、静荷重と低周波動荷重を含む。横0での軸最大値だけを全飛行の上限としたり、軸/横を独立の矩形上限にして包絡外を許したりしない。機体側の定常荷重配分とICDを取得してから3DoFの制約へ割り当てる。
- q・qα・曲げモーメント・TVC限界は同一ではない。構造/制御解析で代理制約の妥当性を確認する。主機関停止・再着火・分離の過渡はノード間検査だけでは評価できない。
- RANGEは本体の最終状態だけでは表せない。第1段と投棄物の受動飛行を別trajectoryとして扱い、その初期条件を分離イベントに接続する。方位角・落下領域の非凸性は既知の回廊を固定して段階導入する。
- 上段再着火を含む場合、惰行・推進剤保持/沈降・始動回数・残量・電力/熱条件が必要。標準ミッション図に再着火があることと、任意の時刻で自由に再着火できることは別である。

段階的な制約導入は開発手順として使う。制約を緩めた途中解は「探索用」であり、必要なZ条件が未設定/未実装なら「ZERO基準ケース合格」にしない。パス制約はLGR点だけでなく端点・接続の左右・補間制御・再積分軌道で検査し、上限を超える区間は追加点/区間分割して再求解する。

## 4. LGR転写

### 4.1 規約

右端を含むflipped LGRに統一する（[Garg et al. 2010](https://people.clas.ufl.edu/hager/files/unified.pdf)）。

```text
-1 = τ_0 < τ_1 < ... < τ_N = +1
コロケーション点 τ_1..τ_N : P_N(τ) - P_{N-1}(τ) の根（τ_N = +1 を含む）
状態 X: (N+1) × n_x      制御 U: N × n_u（コロケーション点のみ）
微分行列 D: N × (N+1)    求積重み w: N（次数 2N-2 まで厳密、総和 2）
```

点はLegendre漸化式＋Newton法で求め、Dはバリセントリック形式で組む。小次数の既知値、点の順序、重みの正値性と総和、多項式の微分・求積精度を単体テストで確認する。

初期端点の制御は変数にない。分離直後等で初期制御が必要な場合は、外挿値を明示的に評価・制約する。

### 4.2 メッシュと時間

フェーズ内は `Phase -> MeshInterval -> Nodes` とし、**最初から複数区間（例: 1フェーズ4〜10区間×次数4〜8）を使う**。推力テーブルの折れ点や大気層境界をまたぐと高次多項式の精度が落ちるため、1区間で次数を上げるより区間分割を優先する。区間比は固定し、区間境界では状態連続とする。

```text
t_i = a + c_i h,   c_i = (τ_i + 1)/2       a: 区間開始, h: 区間長
R_i = Σ_j D_ij X_j - (h/2) f(t_i, X_i, U_i, t_phase_start, p) = 0
```

自由変数はフェーズ時間長だけとし、開始時刻は前フェーズまでの和で作る。絶対時刻と時間長を重複して変数にしない。

規模の目安（7状態・2制御、各フェーズ1区間）: 変数 `Σ_p [7(N_p+1) + 2N_p] + 自由時間数 + 1`、運動方程式 `Σ_p 7N_p` 行。複数区間では `Σ_interval [7(N_k+1) + 2N_k]` に区間接続を加える（共有端点を変数として統合する場合はその分を除く）。3フェーズ×40点は約1100変数だが、ZEROの上段惰行・再着火、積算熱、投棄物の分岐を加えた規模は台帳から数え直す。ヤコビアンは区間内のD由来の密ブロックと、ノード局所の物理微分、自由時間による密な列からなる。

## 5. 微分とスケーリング

### 5.1 TNLPへの対応

| TNLP | 内容 |
| --- | --- |
| `get_nlp_info` | 変数・制約数、ヤコビアン・Hessianの非ゼロ数、`IndexStyle::C` |
| `get_bounds_info` / `get_starting_point` | 無次元化した上下限、RK45由来の初期推定 |
| `eval_f` / `eval_grad_f` | 目的と解析勾配 |
| `eval_g` / `eval_jac_g` | 制約値と疎ヤコビアン（`SparsityRequest::Structure` / `Values`） |
| `eval_h` | L-BFGS期は未使用（`hessian_approximation=limited-memory` を明示）。厳密Hessian導入後は下三角を返す |
| `intermediate_callback` | 反復診断の収集と中断（`false` で `User_Requested_Stop`） |
| `finalize_solution` | 全主変数・双対変数の保存 |

pounceの微分検査 `derivative_test=first-order`（`second-order`）を、PR 0以降の全段階の接続試験で使う。

### 5.2 微分の分担

| 対象 | 方法 |
| --- | --- |
| 目的、`D X`、位置・速度接続、固定質量の投棄、時間の和 | 解析微分（線形または定数） |
| ノードの `f` と動圧・迎角等の派生量 | 前進モードAD。入力は `[x(7), u(2), t, t_phase_start, 直接依存するp]` 程度 |
| 終端軌道条件・イベント写像 | 境界単位の前進AD |

数千変数の双対数をノードに持たせず、ノードごとに小さな局所ヤコビアンを求めて既知の疎構造へ配置する。入力次元が固定なので `DualSVec<f64, f64, K>` で1回評価すればよい。

区間長 `h` と時刻の連鎖は転写側で明示的に組む。

```text
∂R_i/∂X_j = D_ij I - δ_ij (h/2) A_i,    A_i = ∂f/∂x
∂R_i/∂U_j =        - δ_ij (h/2) B_i,    B_i = ∂f/∂u
∂R_i/∂q   = -(∂h/∂q) f_i/2 - (h/2)[ f_t ∂t_i/∂q + f_start ∂t_phase_start/∂q + f_q ]
```

先行フェーズの時間長は後続フェーズの絶対時刻を動かすが、段内時刻 `t - t_phase_start` で決まる推力には相殺がある。絶対時刻だけで微分すると誤るため、`t` と `t_phase_start` を別入力としてADに渡す。

疎構造は実行点のゼロ判定ではなく依存関係から決める。同じ要素へのDと `A_i` の寄与は加算して1要素で返す。`new_x` によるキャッシュは、値と微分が同じ点を参照するよう管理する。

### 5.3 非滑らかさ

ADは折れ点を滑らかにしない。

- 段切替・着火・停止はフェーズ境界に置く（第3.3節）。
- 補間区間・大気層の選択は実部で行い、区間内の補間は双対数のまま計算する。実部に落として `f64` 関数を呼ぶと微分が消える。
- テーブル節点やクランプ境界では片側微分しかない。必要な箇所だけC1補間（単調性保持のもの）にし、平滑化したモデルは版を分けて元モデルでの再積分結果を保存する。
- 迎角の `acos`、対気速度0、極域の座標変換は定義域と正則化を確認する。

有限差分は、AD化前の暫定実装と、ADと疎組立の独立検証にだけ使う。検証では無次元変数のランダムな点・方向 `v` で `Jv` と中心差分を複数の `ε` で比較し、時間・ペイロード・接続・複数フェーズの自由時間を含める。折れ点をまたぐ差分とADの不一致はADの不具合と判定しない。

### 5.4 スケーリング: 既定案と比較実験

**「物理量をO(1)にすれば十分」「pounceの自動スケーリングは常に切る」とは決めない。** 変数、制約、目的、双対変数、メッシュ、KKT線形系を区別して扱う。以下は試験すべき設計であり、ZEROで最良であるとの実測結果ではない。

[GPOPS-II User’s Guide](https://www.gpops2.com/resources/gpops2UsersGuide.pdf) にはbounds/guess/hybridとメッシュ更新時の再スケーリングの選択肢がある。一方、[Ross et al. (2018)](https://arxiv.org/abs/1810.11073) は最適制御の主・双対のバランスを重視し、自動スケーリングが有利とは限らないことを論じる。従って手法名で正解を決めず、同一の物理問題・初期軌道で比較する。

#### A. 物理量に基づく再現可能な出発点

基準量の候補は次のとおり。これらを唯一の正解にはせず、フェーズ別質量尺度や変数範囲による尺度も試す。

| 量 | 初期候補と注意 |
| --- | --- |
| 距離 `L` | 基準軌道半径6,878,137 m。ECI位置各成分は地心原点のまま同じLで割る。高度・地表クリアランスは別の制約尺度を使う。 |
| 速度 `V` | `sqrt(μ/L)` ≈ 7,612.61 m/s。 |
| 時間 `T` | `L/V` ≈ 903.52 s。フェーズ時間変数には実用的な許容範囲/代表時間を別に選ぶ案も比較する。 |
| 質量 `M` | 機体データから計算した初期全質量を固定して使用。求解中のペイロード変数で尺度を更新しない。上段まで同じMを使う案と、フェーズ別質量尺度の案を比較する。 |
| 制御 | 角度はradを基準にし、実際の許容変化幅も考慮する。固定姿勢/固定変数の幅0で除算しない。 |
| 目的 `F_ref` | ペイロードの代表質量。71 t級の全機質量で目的まで割ると目的勾配が過小になり得るため別に選ぶ。広告上の打上げ能力を最適化の質量上限に置き換えない。 |
| パス・イベント制約 | q、比力、熱、残量、投入、時間差など各量の意味に沿う代表値。上限0の条件をその上限で除算しない。 |

数値は既存 `μ = 3.986004418e14 m³/s²` と上記Lから計算した提案例で、ZEROの未公開物理量の推定ではない。

```text
z = z_ref + S_z z_hat          # S_z: 正の対角尺度
c_hat = S_c^-1 c(z)            # 端点・パス・接続・残差の各行
f_hat = s_f f(z),  s_f = 1/F_ref
J_hat = S_c^-1 J S_z

R_hat_i = S_x,p^-1 [Σ_j D_ij X_j - h/2 f_i]
```

上式の `f(z)` は未スケール目的（`-m_payload`）であり、第3.4節の変換後目的を再び `F_ref` で割らない。変数の上下限・初期値、制約の上下限、目的勾配・ヤコビアン・Hessianにも同じ写像を適用する。無限境界は意味として保持し、ソルバー用sentinelを機械的に倍率変換して有限境界へ変えない。

Defectには状態尺度を適用し、時間長が短いからという理由だけで残差を小さく見せない。`R/h` の微分形式を追加で比較する場合は短区間での過大増幅と時間微分まで検査する。異なる質量尺度のフェーズ間接続は、一旦SIへ戻して共通の接続尺度で正規化する。区間ごとに `D` の最大要素へ盲目的に合わせるとメッシュ変更で制約の重みが変わるため、まず状態/制約種別で共通の尺度を使う。

#### B. 3つの層を分けて切替可能にする

| 層 | 候補 | 保持すべきルール |
| --- | --- | --- |
| アプリの変数変換 | 物理尺度 / 有限で妥当なboundsの中点・半幅 / 初期軌道レンジ / フェーズ別尺度 | 広すぎるbounds、固定変数、変化0の初期軌道、角度の折返しを処理する。小幅にはfloor、過大係数にはcapを設けて記録する。 |
| NLPの行・目的尺度 | 物理尺度のみ / 無次元化後の局所ヤコビアン行ノルムによる補正 / pounce gradient-based | 値の大きさと微分の大きさの両方を見る。ゼロ近傍勾配を逆数で増幅しない。可能なら複数の有効な初期推定・代表点を用い、ノードごとの極端な係数を避けて種別で集約する。 |
| KKT線形系 | pounceのnone / Ruiz / slack-based、およびFERAL内部の設定 | NLPの単位変換と別物。因子分解の数値条件改善として独立に比較し、二重という理由だけで一律に禁止しない。 |

[pounce Scalingガイド](https://github.com/jkitchin/pounce/blob/main/docs/src/scaling.md) を確認した。`gradient-based` は初期点の勾配に依存するため、単一点で適切に選べるとは限らない。`curvature-based` は二次以下のモデルを対象とする方式であり、重力・空力を含む本問題の候補にしない。`equilibration-based` は確認したmainのoptions説明でgradient-based相当として扱われており、独立の方法として数えない。登録済みオプション名と実装済み機能は別なので、採用版の挙動を小問題で確認する。

基準設定S0は、**アプリ側の物理尺度 + `nlp_scaling_method=none` + KKT側は上流既定**。これは比較の出発点であり最終推奨の確定値ではない。次に無次元TNLPへ `gradient-based` を追加すること自体は許し、実効係数を保存する。`user-scaling` を使う場合は、アプリで変換済みの尺度をもう一度同じ係数で渡さない。係数は1経路から生成し、明示した追加補正だけを重ねる。

アプリ/NLPの係数は1回の求解中に固定する。初期値変更・メッシュ更新後の再推定は別の求解として履歴に残す。KKTの反復依存スケーリングはこのルールと別である。変換を変えたら元のSI値から初期値と双対を再写像し、古いL-BFGS履歴を流用しない。

#### C. 許容値と双対を混同しない

制約台帳には `physical_limit`、`validation_tolerance`、`scale` を別々に保存する。緩いスケールで小さく見せても、SI単位の制約違反は変わらない。全行を極小の物理許容誤差で割るだけの方法は、ヤコビアンや目的とのバランスを悪化させ得る。`tol` 一つから投入誤差・荷重超過・メッシュ誤差を保証しない。

TNLPへアプリが渡す値は既に変換後なので、pounceが返す「unscaled」は通常**TNLPの単位**であり、SIとは限らない。二段階の逆変換を実装する。`f_hat=s_f f`, `c_hat=S_c^-1 c` なら、pounce内部の尺度を戻した後の双対 `lambda_hat` に対し、物理単位の制約乗数は `lambda = S_c^-T lambda_hat / s_f`。変数上下限の乗数も `S_z^-T / s_f` で戻す。追加の行/目的補正を使う場合はその係数も含める。kg単位の限界性能や制約感度の比較は、この変換を検査してから行う。

線形系のpivot・backsolve残差やKKT誤差と、SIの投入・パス制約を並べて記録する。単に係数がO(1)であることや、ヤコビアン要素の最大/最小比だけで「良条件」と断定しない。近従属な拘束やゼロ勾配は尺度変更だけでは直らない。

#### D. スケーリングの比較試験を実装要件にする

1. S0（物理尺度）を基準に、S1（bounds/初期軌道に基づく変数尺度）、S2（S0＋代表点ヤコビアンの行補正）、S3（S0＋pounce gradient-based）を比較する。最初は変更層を一つに絞る。
2. 上位の候補についてKKTのnone/Ruiz/slack-basedを別に比較する。on-demandの設定を固定し、実際にスケーリングが発動したかも記録する。
3. 小問題 → 単段 → ZERO仮モデル → データ確定ZEROの順に、少なくとも3つの初期軌道、粗/細メッシュ、L-BFGS/厳密Hessianで段階評価する。全組合せを最初から回す必要はない。元のSI初期軌道・制約・計算予算をそろえる。
4. 合格率、SIでの最悪制約違反と投入誤差、ペイロード、反復/復元回数、微分/因子分解の時間、総時間、WASMメモリを保存する。最速の単発解だけで選ばず、再積分合格率と再現性を優先する。
5. 同じ物理問題をm↔km、kg↔t、Pa↔kPaで表現しても、逆変換した評価・微分が許容差内で一致することを検査する。既知解の小問題では解も照合し、非凸なZERO問題ではSIでの実行可能性・性能と局所解の差を記録する。浮動小数点の探索経路が変わるため、同じ局所解へ必ず到達するとは要求しない。物理許容値を固定し、表示単位で問題を変えない。

`ScalingStrategy` は変数/行/目的の係数、推定方法・参照点、floor/cap、pounce・線形ソルバー側の設定を版付きで返す。既定値はこの比較後に決め、失敗時に自動で設定を切り替える場合も、各試行を独立した実行として保存・表示する。

### 5.5 Hessian

GELATOもIpoptの `hessian_approximation=limited-memory` を既定にしており、同種の問題でL-BFGSが実用になることは示されている。ただし反復数や計算時間の優劣はこの問題では未測定であり、改善倍率を仮定しない。ノード局所関数の `λᵀf` はnum-dualの二階双対数でも微分できるが、自由時間の交差項・追加制約・WASMメモリまで含めて実装と費用を比較する。

そこでL-BFGSを既定とし、小問題（PR 3）で厳密Hessian版も実装して反復数・計算時間・頑健性を比較し、多段問題での既定を決める。Hessianはノード単位のブロック対角に、自由時間と状態・制御の交差項が加わる構造であり、`obj_factor·∇²f + Σ λ_k ∇²g_k` の下三角を疎に組み立てて `derivative_test=second-order` で検証する。全NLPの有限差分二階微分は使わない。

## 6. 初期値生成と再積分検証

**初期値。** 既存姿勢履歴でフェーズ単位に順計算し、LGR点へサンプリングする。分離前後の質量・制御を1本の補間でつながない。目標軌道に届かない場合は終端条件を徐々に近付ける継続法を使う。既存サンプルが軌道投入可能な機体とは仮定しない。

**再積分。** 最適化制御を復元し、補強したRK45で初期状態から順に積分する。フェーズ境界で厳密に止めてイベント写像を適用し、後続フェーズを最適化ノード状態でリセットしない。

ZEROの初期推定は、質量・イベントを整合させた仮モデルから作る。長い上段惰行を直接投入と同じメッシュ密度で一様に埋めず、着火/停止付近と急なパス制約の近傍へ区間を置く。公開ミッション図の時刻を硬い制約にせず、機体側が許すシーケンスで継続法を使う。

確認する項目:

1. 再積分軌道とノード状態の差、投入誤差、段別質量収支。
2. 第3.4節の台帳の全適用項目。動圧・空力荷重・比力・方向変化率・投棄後の熱・残推進剤等について最悪値・余裕・発生時刻をSI単位で記録する。イベントの左右、初期制御の外挿、検査点を加える。分離物は本体と別に伝播し、落下点・回廊を検査する。
3. RK45許容値を厳しくしたときの結果の安定性。
4. 手動でメッシュを細分化し前回解からwarm startしたときの、ペイロード・投入誤差・パス制約の変化。

区間ごとに状態多項式の微分と `f(t,x,u)` の差をノード間で評価すると、細分化すべき区間が分かる。密サンプリングは連続時間制約の保証ではない。

結果は `solver_status`（収束・反復上限・中断・実行不能判定等）と `validation_status`（再積分の合否）を別々に持つ。反復上限や中断を成功扱いしない。合否閾値は問題設定に保存する。初期数値試験の位置1 m・速度0.01 m/s等はソフトウェア検証用の仮値で、ZEROの運用許容誤差を意味しない。500 km / 43°では再積分した近地点・遠地点・傾斜角を必ず表示し、ミッションの許容値、メッシュ誤差、積分誤差を分ける。上限超過を許す検証誤差と、設計上確保する余裕も別の入力とする。

**モデル範囲と分散の検証。** 名目最適化に合格してから、風・密度・推力/Isp・質量・分離/停止時刻の分散を版付きシナリオで評価する。シナリオがなければ「名目のみ」と表示する。設計余裕を引いた制約、固定の最悪ケース群、多シナリオ最適化は段階的な拡張であり、任意の一律安全係数やnominalの合格から実飛行での成立を推定しない。確率保証を出す場合は分布・相関・試行数・信頼水準が別途必要。

**合格の分離。** `solver_status`、`validation_status` に加え `constraint_coverage`（設定済み/実装済み/検査済み/未評価）、`model_fidelity`、`mission_profile` を保存する。探索用の省略制約、3DoFで未評価の過渡、飛行回廊の未設定を残したまま「全要件合格」と表示しない。回帰用の仮モデルの成功と、ZEROデータ確定ケースの成功は別の基準とする。

## 7. Rust構成とブラウザ実行

### 7.1 モジュール

既存crate内にfeature `optimization` で追加し、依存の分離が必要になってからworkspace化する。

```text
src/dynamics.rs              共通物理評価、制御・フェーズ文脈
src/optimization/
  problem.rs                 基準ミッション、フェーズ、質量、上下限
  constraints.rs             制約台帳、適用域、物理余裕、評価状態
  lgr.rs                     点、D、w、補間
  transcription.rs           変数・制約配置、名前対応、疎構造
  derivatives.rs             局所AD、解析微分、疎組立、検証
  scaling.rs                 ScalingStrategy、係数生成・逆変換・比較設定
  tnlp.rs                    pounce TNLP実装、全解取得
  initialization.rs          順計算による初期推定、warm start
  validation.rs              制御復元、本体/分離物の再積分、検証報告
```

既存CLI・CSV・summary JSONは変えない。最適化の設定と結果は独立したschema versionを持ち、結果から既存グラフ用の `Sample[]`（`Flight`のsamples） を生成する変換を用意する。結果には入力、コードrevision、ソルバー版、機体/制約データの版・出典・未確定値、メッシュ、スケーリング全層の実効係数、変数配置、全解、終了理由、台帳の適用・検査状況、検証報告を含め、次回の初期値として読み込めるようにする。

### 7.2 WASMとWorker

pounceは `wasm32-wasip1` を前提とする（`std::time::Instant::now()` が `wasm32-unknown-unknown` ではpanicするため）。したがって:

- 既存シミュレータWASM（wasm-bindgen）はそのまま残し、最適化は**別のWASMモジュール**としてビルドする。
- 最適化WASMはwasm-bindgenを使わず、上流と同じく小さなWASI shim（`clock_time_get`・`fd_write`）と、長さ付きJSONの独自ABI（設定入力、進捗・結果出力）でWorkerとやり取りする。
- 公開されている `.nl` 用WASMは使わない。共通物理とpounceを一緒にリンクした独自ラッパーを作る。

```text
React (設定編集) → JSON + 実行ID → Web Worker [最適化WASM]
   RK45初期推定 → LGR転写 → pounce求解 → RK45再積分検証
← 進捗 / 名前付き全解 / 軌道 / 検証報告 → React (グラフ・診断・比較)
```

**中断。** 求解はWASMへの1回の同期呼出しなので、Workerは途中でメッセージを処理できない。候補は3つあり、PR 0で比較して決める。

1. WASI shimにホスト関数 `should_stop()` を追加し、`intermediate_callback` から呼ぶ。JS側はメインスレッドが書く `SharedArrayBuffer` を `Atomics.load` で読む。cross-origin isolation（COOP/COEPヘッダ）が必要。
2. `max_iter` を小さくして求解を分割し、呼出しの合間にメッセージを処理して、返った反復点からwarm startで再開する。COOP/COEPは不要だが、バリアパラメータ等の連続性が一部失われる。
3. `worker.terminate()` で停止する。最も単純だが途中解は失われる。

**ライセンス。** pounceはEPL-2.0、本リポジトリはMIT。pounceは改変せずcrates.ioの依存として使い、配布するWASMにEPLの表示とソース入手先を同梱する。pounceを改変・同梱する場合は、改変部をEPLで公開する必要がある。pounceは2026年5月公開の若いプロジェクトで版更新が速いため、`=0.12.0` のように完全一致で固定し、更新は回帰問題を通してから行う。

### 7.3 UI

既存の設定フォーム・グラフを基礎に「シミュレーション / 軌道最適化」を切り替える。最初の実装は「フォーム → 問題確認 → Worker求解 → 自動検証 → 2件の比較」に絞る。

**2026-10-19の実装状況。** 仮定した多段機とMOMO単段について、ミッション・機体質量・時間上下限・制約・数値設定のフォーム、初期推定/再積分のシーケンス、共通3D地図と時間カーソル、制約フィルタ、数値診断、2件のSI比較、入力/全結果JSON読込、IndexedDBの下書き・全結果・検索・アーカイブ/復元を実装した。フォームにない構成はJSONで編集する。実行中の入力を固定し、読込記録とブラウザ求解を区別する。ZEROの未設定項目と未評価の物理は引き続き成立条件として扱わず、S1尺度実験・warm startや新しい物理制約は後続とする。操作は[optimization.md](optimization.md#ブラウザでの実行)に記載する。

- 段の質量を乾燥・推進剤・投棄物・ペイロードに分けて入力し、合計を表示する。フェーズ一覧で各時間長を固定/最適化（初期値・上下限）にする。
- 「モデル」画面は式の編集ではなく、状態・制御・自由時間・制約・スケール・変数数・疎構造の確認に使う。任意式の編集は初期版では扱わない。
- 進捗は段階名・反復数・目的値・最大制約違反を間引いて表示する。根拠のない完了率は出さない。
- 結果は「求解終了理由」と「再積分検証」を並べて示す。検証不合格でも診断用に残す。実行不能性を証明していない終了を「解なし」と表示しない。
- 実行IDと入力版を固定し、実行中の編集で古い解を上書きしない。warm startでは変数名・フェーズ・メッシュを対応付け、構造が変わったら補間し直す。
- 大きな結果・履歴はIndexedDBに置く。

- [Ross et al. (2018), Scaling and Balancing for High-Performance Computation of Optimal Controls](https://arxiv.org/abs/1810.11073): 物理的無次元化だけでなく主・双対のバランスを考える根拠。
- [pounce Scalingガイド](https://github.com/jkitchin/pounce/blob/main/docs/src/scaling.md) と [Ipopt NLP Scaling / termination options](https://coin-or.github.io/Ipopt/OPTIONS.html): NLPとKKTの層分け、尺度と終了判定。pounceの実対応は採用revisionで再確認する。
- [Ruiz (2001), A Scaling Algorithm to Equilibrate Both Rows and Columns Norms in Matrices](https://cerfacs.fr/wp-content/uploads/2017/06/14_DanielRuiz.pdf): 線形系の平衡化。NLPの物理尺度と区別する。
